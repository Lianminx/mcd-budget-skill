# 麦麦预算搭配师

把“多少钱、想吃什么”变成有门店、有组成、有价格依据的候选方案。本版以到店自取、单人即时用餐为范围；外送、团餐、预约和自动下单不在本版执行范围。

## 输入与工具

确认总预算（元）、城市及公共地标、到店自取方式、想吃的主食、必须包含的小食或饮料，以及用户主动提出的营养偏好。不要自行推测用户位置；缺少地点时可以先查询营养数据，暂不承诺可买或实际价格。医学问题不转换为治疗性搭配。

从本轮工具清单核对下面的麦当劳工具；客户端可能给名称加前缀，使用真实清单中的名称。未挂载 MCP 时，说明缺失；若运行环境支持 Python 且用户已配置 `MCD_MCP_TOKEN`，可用 [mcp_client.py](scripts/mcp_client.py) 查询。Key 只放环境变量，不写入输入 JSON、聊天示例或证据。

调用前读取 [MCP 流程及参数](references/mcp-flow.md)。参考文档记录的是 2026-10-10 实测合同，实际参数以本轮 `tools/list` 为准。

## 搭配流程

1. 用 `query-nearby-stores` 按用户城市和地标搜索到店自取门店（`searchType=2, beType=1`），让用户选择门店；用户已授权自动选店时才自行选择。确认门店营业状态。
2. 查询同一门店的 `query-meals`、`query-store-coupons`，保持 `storeCode, orderType=1, beType=1` 一致，不传 `beCode`。没有合适券就按菜单搭配，不声称已领券。
3. 用 `list-nutrition-foods` 获取营养数据。严格匹配品名、规格、数量；相同品名多条数据冲突或没有数据时标为未知，不能把未知记为零。套餐须先用 `query-meal-detail` 取得实际默认组成、规格和 `roundList`，按组成计算营养，不能把整个套餐当作一个汉堡。实际选中项以 `quantity>0` 为准；实测部分 round 有多个 `isDefault=1`，不能全部加入。已有套餐内的饮料、小食不能重复计入。
4. 建立小规模候选集：保留真实商品编码、菜单价格来源、券条件、套餐组成、营养匹配依据。无需凑满预算。可以分别尝试省钱、蛋白质优先和包含小食饮料的方案；只输出满足用户要求的方案，不强凑三种。价格缺失不编造；券不能默认叠加。同一张券不能用于多个商品。
5. 可用 [预算计算脚本](scripts/plan.py) 排序候选。输入格式见 [候选数据合同](references/candidates.md)。脚本只根据输入枚举“一个主食或套餐 + 可选小食 + 可选饮料”，输出状态始终是待报价核验；它不会读取门店菜单、自动推断券规则，也不保证全菜单最优。券后总价可能低于菜单估价，额外考虑有实际适用优惠的候选，不能仅因估价超过预算就排除。`canWithOrder=true` 或依赖购卡、会员的价格不能作为无条件售价；本版避开购卡商品。
6. 对准备展示的每个方案调用 `calculate-price`，包含实际商品编码、数量、券及套餐子项。也可用 [报价脚本](scripts/quote.py) 核验本地候选，实际成功响应的 `data.price` 是总应付金额，`productList` 用于核对商品数量。金额从分转换为元，包含接口返回的所有费用，不另减一次优惠。核验后超预算就淘汰或替换重算。报价失败只修正一次明确输入错误；仍失败就保留“待核验”候选，说明无法确认实际价格。网络错误不转为“无可用券”。报价没有返回券核销依据时，只声称总价已核验，不声称指定券已成功使用。

## 交付

展示门店、取餐方式、查询时间、预算和方案表。每个方案包含餐品及数量、接口应付金额、预算余量、热量和蛋白质（有完整数据时）、用券条件及推荐理由。把未核验候选与核验通过方案分开展示；没有可行方案就指出哪项约束无法满足，让用户选择调整预算或偏好。

保留价格核验的工具名、时间和脱敏回执摘要，方便复核。不得把示例数据描述为真实报价。说明本次结果仅在本次门店、时间、方式和券条件下成立，营养信息用于一般参考。

本 Skill 不调用领券、兑换积分、抽奖、创建或取消订单工具。用户要求下单时交回宿主点餐流程，确认商品、门店和费用后再按其授权执行。
